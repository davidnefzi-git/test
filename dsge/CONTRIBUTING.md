# Contributing to the DSGE knowledge base

Contributions are welcome. The repository is designed as a scientific knowledge base for
canonical DSGE models and reusable structural mechanisms. Contributions should improve
the accuracy, traceability or reusability of that knowledge without turning the library
into a general estimation or model-design application.

All scientific documentation and metadata must be written in **English**.

## 1. Before editing

Read:

1. `README.md` for repository scope;
2. `docs/model-documentation-policy.md` for model-level documentation rules;
3. `docs/composition/README.md` for component contracts;
4. the relevant file in `docs/theory/` before changing an equation used by an existing
   mechanism.

Use the primary publication whenever possible. Do not infer an equation number, prior,
calibration or empirical result from memory when the source can be checked.

## 2. Repository structure

- `components/<id>/component.yaml`: reusable mechanisms and their equation contracts;
- `models/<id>/manifest.yaml`: canonical model composition and scope;
- `models/<id>/spec/model.md`: model-specific theoretical description;
- `models/<id>/estimation.yaml`: empirical reference for estimated canonical models
  only;
- `models/<id>/spec/estimation.md`: interpretation of that estimation reference;
- `models/<id>/golden/targets.yaml`: enduring verification targets;
- `docs/theory/`: reusable derivations;
- `taxonomy/`: controlled variable, parameter, family and mechanism vocabulary;
- `schema/`: machine-readable structural contracts;
- `tests/`: maintenance and integrity checks.

## 3. Component rules

A component must declare all variables it provides and requires. Every symbol appearing
in an equation must resolve to a declared variable, parameter or shock.

Use `replaces`, `depends_on`, `incompatible_with` and `compatible_cores` to
express structural interfaces explicitly. Do not rely on an existing model happening to
supply a missing variable.

Each equation must have:

- a stable `id`;
- its residual expression in `expr`;
- a scientific `status`: `original`, `derived`, `adapted`, `standard` or
  `unverified`;
- a `source_check`: `verified_primary`, `verified_working_paper`, `pending` or
  `standard_identity`;
- a `source` when the relation is source-specific;
- a `derivation` pointer when the equation is derived or adapted.

Do not use one parameter name for two economic objects. Update
`taxonomy/parameters.yaml` when a symbol is intentionally shared across components.

## 4. Theory documents

Theory documents should explain the chain from primitives to the equation stored in the
component:

$$
\text{primitives and constraints}
\rightarrow
\text{first-order conditions}
\rightarrow
\text{equilibrium}
\rightarrow
\text{steady state}
\rightarrow
\text{approximation}.
$$

Not every component requires every step. Identities, policy rules and exogenous
processes should be documented according to what they actually are.

A reusable derivation should appear once. Components point to it; model specifications
should not maintain a second independent derivation.

## 5. GitHub Markdown conventions

Use GitHub-compatible Markdown consistently.

- headings: `#`, `##`, `###`;
- inline mathematics: `$...$`;
- display mathematics: a separate `$$ ... $$` block;
- tables: standard pipe-table syntax;
- code, paths and identifiers: backticks;
- links: relative Markdown links for repository files.

Do not encode ordinary prose as HTML entities. Do not use raw HTML to repair formatting
that standard GitHub Markdown already supports.

Keep equations readable in the source. Prefer one mathematical statement per display
block when the derivation is nontrivial.

## 6. Model documentation

Follow `docs/model-documentation-policy.md`.

A theoretical or calibrated canonical model should not contain an invented estimation
procedure.

An estimated canonical model must document the estimation method when that method is part
of the published model. For Bayesian models this includes the measurement system,
priors, likelihood, posterior computation and published posterior evidence.

Published estimates are reference information. They must never be presented as results
generated by this repository unless the estimation has actually been reproduced.

## 7. Provenance and scientific tone

Keep scientific files free of development-history noise.

Do **not** add:

- local upload filenames or comments about filename mistakes;
- statements that a source was scanned, uploaded or supplied through a particular tool;
- `ingested_by` or `ingested_on` metadata;
- AI/model names as scientific provenance;
- obsolete bug stories or narratives about how a correction was discovered;
- counts or runtimes from a particular test execution.

Git history, pull requests and CI logs already preserve development history.

Do retain information that changes the scientific interpretation: alternative
normalisations, source-version differences, unresolved derivations, missing primary
sources and genuine model restrictions.

## 8. Golden targets and tests

Golden targets should encode enduring model properties:

- analytical solutions;
- nesting limits;
- sign or normalization restrictions;
- reference numerical quantities that are scientifically meaningful.

Do not use a golden file as a test log.

Tests may check syntax, interfaces, references, equation counts, nesting properties and
numerical consistency. A passing test does not by itself establish source fidelity.

Before opening a pull request, run from `dsge/`:

```bash
python -m pytest -q
```

If a model entry has dedicated golden targets, run the relevant `modellib golden`
command as well.

## 9. Adding a canonical model

A new model entry should:

1. identify the exact primary reference;
2. state whether the entry is theoretical/calibrated or estimated;
3. reuse existing components where their economic assumptions match;
4. add a new component only when the mechanism is genuinely different;
5. document model-specific assumptions in `spec/model.md`;
6. add estimation resources only when required by the canonical methodology;
7. add golden targets that test economically meaningful properties;
8. update repository indexes and taxonomies where necessary.

Do not copy a complete model into a new monolithic file when its mechanisms already
exist as reusable components.

## 10. Pull-request checklist

Before requesting review, confirm that:

- primary references and equation numbers have been checked;
- Markdown renders correctly on GitHub;
- no development-history metadata was added to scientific files;
- all new variables and parameters are registered consistently;
- model IDs and internal links resolve;
- theoretical and empirical documentation follow the model's actual methodology;
- the full test suite passes;
- the pull request explains any change that modifies an economic equation, parameter
  normalization or published reference value.
